# MyWhoosh互換性の確認状況

更新日: 2026-10-21。
**ZWO出力は試験機能です。公式MyWhoosh Workout Builderへの取り込みは、以下の4種類についてユーザー確認済みです。確認範囲は区間数・合計時間の期待値との一致です。**
**MyWhooshアプリへの同期、実走時の出力制御、他のOSや環境での互換性は未検証です。**
既存のJSON保存とは独立して実装しています。今回の取り込み結果はユーザーの実施報告に基づき、Codexによる独立した再検証ではありません。CodexはMyWhooshアカウントへのログインや登録操作を行っていません。

## 確認済み

### ユーザーによる公式Workout Builderへの取り込み確認

報告の記録日: 2026-10-21。確認主体: ユーザー。取り込み先: 公式MyWhoosh Workout Builder。
以下の4種類を取り込み、区間数と合計時間が期待値どおりだったとの報告を受けました。

| ワークアウト | 期待区間数 | 期待合計時間 | ユーザー確認結果 |
| --- | ---: | ---: | --- |
| 計算サンプル | 3 | 10分（600秒） | 区間数・合計時間とも一致 |
| SST | 5 | 50分（3000秒） | 区間数・合計時間とも一致 |
| 4×8 | 9 | 56分（3360秒） | 区間数・合計時間とも一致 |
| 30/15 | 64 | 43分30秒（2610秒） | 区間数・合計時間とも一致 |

これにより、この4種類のZWOについて公式Builderでの受理と区間数・合計時間を確認済みとします。
個々の区間時間・区間順・FTP比率・目標W、アプリへの同期や実走時の出力制御は、この報告からは確認できません。
実際の検証日時、OS・ブラウザ・Builderの版、使用FTP、取り込んだファイルのハッシュは未記録です。
他のOS・環境・ファイルや全てのZWO機能へ、この結果を一般化しません。

## 試験実装の範囲

`exporters.zwo.to_zwo(workout)`は標準ライブラリの`xml.etree.ElementTree`でUTF-8 XMLを生成します。
モデル・JSONスキーマは変更していません。ネットワークアクセスやサーバーへのファイル保存もしません。

| モデル | 出力 |
| --- | --- |
| ワークアウト名・説明 | `name`・`description`。特殊文字はエスケープし、内容を保持 |
| 区間時間 | `SteadyState`の`Duration`。整数秒 |
| 目標%FTP | `Power`。十進表記を100で割った比率 |
| 区間順 | 1区間につき1要素。反復圧縮なし |
| kind（区分） | 形状へ変換しない。全て一定出力。区分情報はJSONに保持 |
| 個別区間名・色 | ZWOには書き出さない。UIとREADMEで明示し、JSONに保持 |
| 作成側FTP | ZWOには埋め込まない。取り込み先FTPでWが変わり得る |

例: 80%は`Power="0.8"`、120%は`Power="1.2"`です。
浮動小数点値はPythonの標準十進表記を基準に変換し、比率を固定小数点文字列で出力します。
`Decimal`の精度設定に依存した丸めや、非常に小さい正数のゼロ化を避けています。
これはMyWhooshがその値や桁数を受け付ける保証ではありません。
XML 1.0で禁止される文字、不正な数値や時間は拒否し、黙って削除・補正しません。
文字参照によりメタデータのCR・CRLFもXML再解析後に保持します。

## MyWhooshでの手動検証

以下は再検証・検証範囲拡張のための手順です。上記4種類のBuilderでの区間数・合計時間はユーザー確認済みです。個々の出力値、アプリ同期、実走時の出力制御、他環境の確認は残っています。Codexはログイン・登録・アップロードを実施していません。

1. 公式Builderでログイン後のインポート形式と注意事項を確認します。残り保存枠も確認します。
   既存のワークアウトを削除したり、有料枠を購入したりする必要が生じた場合は、その場で止めて判断します。
2. 作成側FTPと取り込み先FTP、OS、MyWhooshのバージョン、確認日を記録します。
3. アプリから検証例を読み込んでZWOをダウンロードするか、`examples/calculation_sample.zwo`を使います。
   公式Builderでファイルを選び、受理されるか確認します。構文エラーと保存枠の問題を区別します。
4. 出力例が3区間・合計600秒であることを確認します。
   FTP=250 Wなら、300秒125 W→120秒250 W→180秒125 Wが期待値です。
   FTP=300 Wなら150→300→150 Wです。Wが違う場合はFTPと比率、表示の丸めを調べます。
5. Builderでの確認後、MyWhooshへ送る操作を行い、アプリ内のカスタムワークアウトを開きます。
   区間順・各秒数・合計時間・目標Wをもう一度確認します。未反映なら同期状況を記録します。
6. プリセットをSST（5区間・3000秒）、4×8（9区間・3360秒）、
   30/15（64区間・2610秒）の順に検証します。4×8の最後に不要な3分回復が増えていないかも確認します。
7. 0%FTP、1秒区間、小数比率、日本語・`&`・`<`などの名称は別の境界条件テストとして調べます。
   最小の通常ケースに通ったことだけを、これらの対応保証には使いません。

より広い互換性検証の合格条件は、区間順と各区間の整数秒の一致、取り込み先FTPに対応した目標出力の一致、アプリ内での同内容の確認です。今回のユーザー報告で確認した区間数・合計時間とは分けて扱います。
表示の丸め誤差は、丸め方を確認した場合だけ許容します。実機トレーナーの追従性は別の検証です。
画面・期待値・実際の値・エラーメッセージ・環境を記録し、「XML検査済み」と「MyWhoosh実取り込み済み」を分けます。
